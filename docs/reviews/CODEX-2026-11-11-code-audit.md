## R1 · P1 — Згадка Jarvis усередині фрази стає командою

**Місця:** `Sources/WakeSupport.swift:163`, `Sources/App.swift:1257` в основному проєкті.

`stripLeadingWakeWord` шукає збіг серед перших трьох слів та відкидає всі попередні слова. Цю функцію використовують не лише для обрізання запису з preroll, але й як дозвіл виконати завершений фоновий сегмент у `screen`.

Відтворено на чинному коді:

```text
Вхід: «Я сказав Jarvis закрий Safari»
found=true
IntentParser результату: quitApp("safari")
```

Це суперечить продуктовій специфікації: сегмент стає командою тільки коли **починається** зі слова активації. Згадка назви помічника у звичайній розмові може запустити локальну дію без підтвердження.

**Виправлення:** відокремити дозвіл активації (тільки початок сегмента, явні перевірені варіанти імені) від обрізання preroll у вже активованому записі. Додати негативні приклади зі згадкою імені всередині речення.

## R2 · P1 — Журнал розмов зберігає вміст диктування та потенційні секрети

**Місця:** `Sources/App.swift:982`, `Sources/App.swift:1288`, `Sources/ArcViews.swift:77`, `Sources/ConversationLog.swift:38`.

Перед парсером дій записуються повні `raw` і `shown`; журнал увімкнений за замовчуванням. Тому приватне представлення у `HistoryStore` не захищає диктування: той самий payload уже є у другому журналі. `ConversationLog` не приховує секрети, хоча його контракт каже «Never contains API keys».

Відтворено синтетичним маркером: після запису `heard.raw = "диктуй REVIEW_SENTINEL_SECRET"` JSONL містить `REVIEW_SENTINEL_SECRET` відкритим текстом. Права 0600 працюють, але не прибирають зайве збереження даних.

**Виправлення:** класифікувати та прибирати чутливий payload ДО `logEvent`, не журналювати тіло диктування; для інших текстів визначити явну політику секретів/opt-in. Не обіцяти відсутності ключів у журналі без такого контролю. Збереження звичайних діалогів за бажанням користувача можна лишити окремою функцією.

## R3 · P1 — Старий wake-screen результат може ожити після вимкнення й повторного ввімкнення

**Місця:** `Sources/App.swift:1009`, `Sources/App.swift:1191`, `Sources/App.swift:1242`, `Sources/App.swift:119`.

`cancelSession`/`disableWake` не змінюють `screenToken` і не очищують `screenPending`. `LocalSpeech.screen` ігнорує command generation, перед стартом скидає cancellation, а completion викликає завжди. Guard completion перевіряє тільки старий ticket та **поточний** `canScreen`; epoch аудіо для готової команди не перевіряється.

Сценарій: сегмент уже розпізнається або його completion очікує main queue → користувач вимикає wake/мікрофон → повторно вмикає до приходу результату. `canScreen` знову true, screen ticket той самий — старий сегмент може дійти до `presentScreenedCommand` і executor. Статично перевірено цей шлях; pure-проба підтвердила, що idle-cancel не змінює VoiceMachine.turn та повертає wakeArmed=true. Живе відтворення з мікрофоном не проводилось.

**Виправлення:** інвалідовувати screening ticket та pending segment при cancel/wake-off/mic-off/sleep/model change; перевіряти epoch/generation у completion до створення нового turn. Додати контрольований тест із затриманим callback та off→on.

## R4 · P1 — Після ASR зникають засоби скасування виконання/AI

**Місця:** `Sources/App.swift:987`, `Sources/App.swift:717`, `Sources/ArcViews.swift:448`, `Sources/VoiceState.swift:43`.

Після розпізнавання `disableEscape()` викликається **до** `runCommand`. `VoiceMachine.busy` враховує лише recording/transcribing; тому main/HUD кнопка Cancel прихована, а пункт меню Cancel вимкнений, поки працює executor або AI. Голосове acknowledgment тимчасово повертає Esc, але після закінчення озвучування він знову вимикається, навіть якщо AI ще думає. При вимкнених spokenReplies acknowledgment не допомагає взагалі.

Отже, стандартний сценарій «відпустив PTT → довгий AI-запит → Esc» не викликає Task.cancel. Користувачеві доводиться вимикати весь мікрофон або починати інший turn.

**Виправлення:** єдиний стан активного turn має включати execution/AI/approval; тримати Esc, кнопку та меню Cancel доступними до фактичного завершення або скасування цих частин. Регресія: spokenReplies=false + повільний mock provider + Esc.

## R5 · P2 — Неповне фінальне usage може занизити бюджет

**Місця:** `Sources/Agent/GooseACPClient.swift:96`, `Sources/Agent/BudgetedGooseAgent.swift:63` (цей модуль написаний Codex).

Клієнт зберігає останню додатну ціну та ігнорує наступний usage із `cost: null`/без cost. Runner вважає наявність будь-якої додатної ціни доказом повного обліку (`complete=true`), навіть якщо пізніший usage не містить ціни.

Відтворено локальним ACP mock: usage USD 0.01 → наступний usage зі збільшеним контекстом та `cost:null` → end_turn. Поточний результат:

```text
reported=10000 micro-USD
charged=10000 micro-USD
reserved=250000 micro-USD
```

Ціна попереднього етапу видається за повну ціну запиту, резерв звільняється. Це не доказ конкретного рахунку OpenAI; це підтверджена помилка консервативного обліку при неповних даних, які модуль обіцяв не трактувати як дешевший завершений запит.

**Виправлення:** окремо тримати максимальну відому ціну та ознаку повноти останнього обліку; при втраті ціни не звільняти резерв як при доведеному повному usage. Додати regression для valid cost → null/missing cost → end_turn. Provider-side ліміт усе одно потрібен незалежно від цієї помилки.

## R6 · P2 — «Виконання дій: готово» показується до підтвердження плану

**Місця:** `Sources/App.swift:466`, `Sources/App.swift:499`, `Sources/ArcViews.swift:517`.

При завершенні відповіді AI стадія action одразу стає `.done`, і лише потім відкривається панель підтверджень. Жодної дії ще могло не бути. Якщо користувач відхилить план або реальне виконання завершиться помилкою, `agentPlanFinished` змінює текст/голос, але не виправляє стадію action.

**Виправлення:** відокремити «відповідь AI готова» від «дія виконана», ввести очікування підтвердження, а action status оновлювати тільки за CommandOutcome реального executor, з урахуванням усіх кроків плану.

## R7 · P2 — Повернення TTS-знаків на межі місяця дає від'ємний лічильник

**Місця:** `Sources/SpeechOutput.swift:141`, `Sources/CloudVoice.swift:110`.

Запит резервує знаки в момент відправлення. Якщо він не вдався вже в наступному місяці, refund викликає `record(-count, at: Date())`. `roll` спершу обнуляє новий місяць, після чого віднімається вартість старого.

Відтворення на двох моментах по різні сторони локальної межі місяця:

```text
record(+10, попередній місяць)
record(-10, наступний місяць)
used=-10
allows(110, limit:100)=true
```

**Виправлення:** повертати резерв у місяць початкового запиту за reservation ID; не дозволяти від'ємний used. Не змішувати це з щомісячним обліком OpenAI — це окремий TTS ledger.
