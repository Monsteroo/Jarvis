# Jarvis v0.1 — macOS product design and 10–11-day release scope

Status: user approved the 10–11-day schedule and ARC Current visual direction. Updated 10 November 2026. This document supersedes the original PTT-only and research-only product assumptions; existing source code remains an ASR prototype until implemented and verified.

## Product outcome

A complete single-user native macOS application for Vitalii, running on Apple M1/16GB/macOS14.5. Voice activation by the word “Jarvis”, Ukrainian and English interaction, real voice-reactive visual identity, useful computer actions, visible completion/error feedback and controllable background tasks. The user intends to present a product at a final hackathon in approximately 1.5 weeks; no contest rules or judging criteria have been provided.

A complete v0.1 has an installable app, onboarding, settings, permissions/error recovery, everyday interaction and an inspectable history. The release scope is bounded to capabilities below; “complete” does not imply arbitrary reliable GUI automation across all applications.

## Application surfaces

1. **Menu bar:** app state, voice activation toggle, show main window, microphone off and quit. Optional login item controlled by user.
2. **Compact voice HUD:** floating panel shown by wake word/hotkey, live microphone response, accepted transcript, current action, reply. It must not steal focus from the target field during dictation.
3. **Main window:** voice visualization and conversation, current task list, history and settings. The selected visual language is shared with the HUD.
4. **Onboarding:** local model readiness, microphone permission, Accessibility/Automation only when the chosen action needs them; test wake word and hotkey; clearly show muted/listening states.

## Interaction state machine

Muted → Wake listening → Command listening → Understanding → Executing → Speaking/Result → Wake listening.

- Wake listening is local lightweight detection of “Jarvis”. It does not run unrestricted ASR continuously.
- The user explicitly enables voice activation. A persistent visible mic control disables all capture immediately. PTT remains available as a fallback.
- On trigger, show HUD and play a subtle acknowledgment. Capture a command until end-of-speech or a bounded timeout; retain a short RAM-only preroll to avoid losing the first words.
- Start with single-command interactions. A short bounded follow-up window may be enabled in settings after basic flow is reliable.
- Esc/stop cancels the active turn. A result from a cancelled generation never appears as a new successful action. Remote job cancellation is best effort and does not undo a completed side effect.
- TTS and wake detector must avoid self-triggering. Pause/gate wake detection during app speech, keep hotkey/stop available, then resume explicitly.
- Silence, noise, unavailable model and network failures return the UI to an actionable state.

Wake implementation is subject to the primary-source and target-machine check in docs/research/wakeword-jarvis-macos.md. The required phrase is “Jarvis”; a library shipping only “Hey Jarvis” is not silently treated as equivalent.

## Visual design and motion contract

Approved direction: **ARC Current**, reference `docs/design/jarvis-arc-current.png`. Deep navy glass, cyan and restrained amber, horizontal luminous voice filaments with neural impulses, left navigation, transcript below the visualization, horizontal task progression and a matching compact HUD. Implement the wave form rather than the earlier spherical core. Earlier ARC, PRISM and Nexus concepts remain alternatives only. This is a design reference, not an assertion that the screenshot is already implemented.

Each state must be legible through text and form, not color alone:

| State | Behavior |
|---|---|
| Muted | Inactive core, explicit crossed microphone |
| Wake listening | Low-intensity stable core, minimal resource use |
| Command listening | Envelope and frequency bands react to actual microphone samples |
| Understanding | Small coherent orbit/phase change; preserve transcript |
| Executing | Visible task progression driven by actual tool events |
| Speaking | Motion driven by synthesized audio amplitude/playback state |
| Result/error | Clear completion or recoverable error, then settle |

Amplitude/FFT calculation runs off the main thread; publish a smoothed envelope and limited spectrum bands. Render only when visible and active, target60fps on M1 with an adaptive30fps fallback, respect Reduce Motion. No simulated random “audio response”, invented telemetry or success animations before execution confirms success. The visual renderer does not add latency to ASR/tool dispatch. Prefer SwiftUI Canvas/Metal or AppKit layers within a native window; a local web visualization is a fallback only if it preserves performance and native integration.

## Functional v0.1

- Open, activate and normally quit selected applications by aliases.
- Minimize, maximize and place supported accessible windows left/right; show partial failures honestly.
- Volume/mute and supported brightness/Focus adapters after capability checks and the configured confirmation rule.
- Open URL and browser search.
- Dictate into the previously active supported field; never synthesize Send/Enter as a hidden final step.
- Free-form requests through a selected text LLM and a typed tool registry.
- Prepare an email/message draft with explicit recipient disambiguation; external sending requires per-action approval of the concrete content.
- Start/status/cancel an allowed background workflow. Harvey is one optional integration, not a requirement for opening programs.
- Ukrainian/English TTS response, short by default, visual-only mode available. A fallback Ukrainian voice must be verified rather than assumed present on14.5.
- Local action history, error details, latency stages and budget usage. Secrets and raw room audio do not enter history.

## Reuse and boundaries

Preserve working native ParakeetUK recognition. Goose is the preferred ready-made agent-runtime candidate for complex text tasks, sessions and MCP orchestration; it is not yet installed or proven in this project. First validate a pinned runtime on14.5, custom-client transport, approval events, cancellation and cost reporting. Prefer an adapter/configuration over a large upstream fork. Make a go/no-go decision by the end of day2; if it fails, keep the same typed-tool boundary with a small direct model planner for v0.1 rather than waiting for a replacement framework.

Local simple actions bypass the LLM. An action adapter validates its schema, target and approval before execution, regardless of runtime. No unrestricted shell is needed for the release action set. Cloud receives only selected complex-request text/context; monthly Jarvis model-call ceiling remains $10. Existing API connectors in a chat are not assumed to be automatically available to the standalone app.

The Windows home server can host long workers/workflows; it is not in the critical voice→simple-action path. Do not migrate existing server services as a side effect of app work.

## Release sequence

This is a proposed delivery sequence, not a measured effort estimate or a promise that all work is done.

| Day | Deliverable and gate |
|---|---|
| 1 | Choose visual direction; define shared state/events; build native shell and real audio-reactive core; validate runtime compatibility in isolation |
| 2 | Wake-word integration and mute/PTT fallback; runtime go/no-go based on actual behavior, not README |
| 3–4 | App/window/URL/dictation actions and visible results; safe focus handling; typed action tests |
| 5–6 | Free-form planner/runtime adapter, concrete approvals, cost accounting, short TTS; one background integration |
| 7 | Complete history/settings/onboarding, missing permissions and offline/error flows; feature freeze |
| 8–9 | Real voice tests, noise/false activation tests, cold/warm launch, long run, cancellation and resource tuning; signed local distribution package |
| 10–11 | Release candidate, clean-launch walkthrough, presentation assets and rehearsal; fix defects only |

The continuous end-to-end product flow is kept runnable throughout; do not defer integration to the final days. Presentation uses the same app and actual task results. A recorded walkthrough may back up a live presentation, clearly identified as a recording.

## Acceptance evidence

- Release opens on the target macOS14.5 from its distributable package without developer-directory assumptions.
- Wake word works on the user's voice; log trigger/detection latency and false activations in quiet/noisy conditions. Select thresholds from evidence, not a fabricated zero-false-positive guarantee.
- Audio remains local and unsaved except explicit one-shot diagnostics; microphone-off state closes capture.
- At least20 distinct basic command scenarios verified. Target original simple-command p50≤1s/p95≤2s from actual speech end; report misses honestly. Current Parakeet known-file0.33–0.46s is not a full command SLA.
- No external send/delete/purchase without valid per-action approval; rejection and cancellation paths tested.
- UI animation maps to real audio/task events; main app remains responsive during recognition and execution.
- Model unavailable, no internet, permission revoked, wrong app/contact and background worker failure all produce useful recoverable feedback.
- Document user-authored implementation, adapted code and model/framework attribution; include third-party licenses in the app distribution.
