# Jarvis: готове рішення, fork чи готове ядро

Дата перевірки: 10 листопада 2026. Джерело запиту — надане користувачем дослідження ринку. Це перевірка документації та частини вихідного коду, не аудит дистрибутивів і не runtime-тест перелічених програм. Програми не встановлювали, дозволи й credentials не змінювали.

## Рекомендація

**Використати готове агентне ядро Goose разом із наявним голосовим клієнтом Jarvis/Parakeet; спочатку перевірити цю інтеграцію коротким прототипом.** Не писати власний універсальний agent loop, історію сесій та весь набір інтеграцій. Повний fork готового десктопного застосунку поки має гірше співвідношення користі й переробок під специфічні вимоги.

Це інженерна оцінка за джерелами, а не доведений результат порівняльного запуску. Якщо перевірка Goose на macOS14.5 або його approval-протоколу не пройде, рішення потрібно переглянути.

Поточний стан: у проєкті вже є push-to-talk, нативне вікно, локальний Parakeet UK, контроль запису, діагностика та виміри. Інтегрований адаптер правильно розпізнав один погоджений запис тричі за 0,33–0,46с. Дії macOS, універсальний planner і поштові інтеграції ще не реалізовані. Саме їх варто брати з готових інструментів; наявні голосові виміри не доводять загального SLA.

## Goose: готова частина, яку можна не писати

Поточний репозиторій `block/goose` перенаправляє на `aaif-goose/goose`. Ліцензія Apache-2.0. Документація прямо описує власні дистрибутиви, підключення свого UI до `goose serve` через ACP, MCP-інструменти та recipes. Це значно ближче до бажаного перевикористання, ніж перенесення окремих класів Rust у Swift. Точний transport/API потрібно звірити з обраною pinned версією перед кодом. [Custom distributions](https://github.com/aaif-goose/goose/blob/main/CUSTOM_DISTROS.md).

Найпростіше почати з конфігурації та вузького адаптера, не з форку: менше розходжень із upstream і простіше оновлення. Наш клієнт залишає мікрофон/Parakeet на Mac і передає ядру текст лише для складних задач. Операції на кшталт «відкрий програму» мають іти прямим локальним шляхом, щоб не платити затримкою LLM за кожну дію.

Підтримка macOS/Apple Silicon заявлена в офіційній інструкції встановлення. Перевірений Homebrew cask `block-goose` v1.58.0 указує macOS Monterey як мінімум. Це позитивний сигнал для 14.5, але не замінює запуску конкретного бінарника. [Інструкція](https://goose-docs.ai/docs/getting-started/installation/), [cask](https://github.com/Homebrew/homebrew-cask/blob/master/Casks/b/block-goose.rb).

Goose вже має локальне Whisper-диктування. Але описаний UX — кнопка мікрофона, диктування під час пауз і голосова команда submit — відрізняється від нашого PTT. Наявність диктування не доводить якість української чи вимкнення мікрофона на key-up. [Voice Dictation](https://goose-docs.ai/docs/guides/sessions/in-session-actions/).

Потрібно явно змінити дозволи: документація називає Autonomous типовим режимом. Approve/Smart Approve та індивідуальні tool permissions є, але їхня класифікація не є доказом обов’язкової згоди перед кожним листом або GUI-кліком Send. Таке правило слід забезпечити в нашому вузькому tool-адаптері. [Permissions](https://goose-docs.ai/docs/guides/managing-tools/goose-permissions/).

Не вважати current working directory автоматичною ізоляцією процесу. Ізоляція, права інструмента та згода користувача — різні механізми. Для Mac достатньо вузьких перевірених дій; довільне виконання коду не потрібне для першого набору команд.

Наявність keyring теж не універсальна гарантія: у Goose є file-based secrets fallback. Для нашого Mac перевірити саме Keychain і не дозволяти тихий перехід на plaintext у запропонованій конфігурації. Жорсткий ліміт $10 не виведено з документації permissions; його треба реалізувати/довести окремо на всіх model calls, включно з retry і внутрішніми викликами. [Config files](https://goose-docs.ai/docs/guides/config-files/).

## Чому не весь isair/jarvis

Окрема перевірка pinned commit `f2b7e375be1579133bea4aa1306e09473f9c9a0b`: [isair-jarvis-fit.md](./isair-jarvis-fit.md). Це реальний Python/PyQt6/WebEngine застосунок із готовим arm64 релізом v2.8.0, а не порожній репозиторій. Однак command listener запускається у фоні; dictation має окремий hands-free шлях; розпізнавання передає `language=None`. Щоб виконати наші вимоги, доведеться міняти голосовий контур і передусім gate виконання інструментів. Сумісність готового release з14.5 не перевірена.

Описаний REST належить Memory Viewer, а не універсальному API виконання задач. Personal/noncommercial використання ліцензія дозволяє, отже для поточного особистого проєкту це не автоматична заборона. Але перенесений код теж має ліцензійні умови, на відміну від Apache-2.0 Goose. Детальні source links і відмінність перевіреного HEAD від релізу — в окремій нотатці.

## Що неточно в наданому дослідженні

1. **«Goose не має голосу» — застаріло.** Є локальний і хмарні dictation providers; це не означає, що їхній default UX відповідає нашим вимогам. Джерело вище.
2. **«01 має високу зрілість» — перебільшено.** Сам README попереджає про експериментальність і відсутність базових safeguards до stable1.0. Код 01 має AGPL-3.0; це не та сама ліцензія, що в усіх пов’язаних репозиторіях. [README](https://github.com/openinterpreter/01).
3. **«Browser Use безпечно обробляє секрети завдяки Chromium sandbox» — надто широке твердження.** Поточний README прямо пояснює, що модельний Python може читати передані secrets, а browser helpers/domain guards не є пісочницею агента. Default-конфігурація також може використати хмарні браузер/модель. Локальний режим треба задавати явно. [README](https://github.com/browser-use/browser-use).
4. **«Жодне рішення не містить шкідливого коду» — не доведено.** Для такого висновку потрібен аудит конкретних дистрибутивів/залежностей; ні дослідження без джерел, ні наша коротка перевірка його не встановлюють.
5. **CVE потрібно читати з умовами експлуатації.** Наприклад, опис наведеної Android press_key проблеми UFO в офіційному advisory вимагає автентифікованого Mobile MCP caller і підключеного авторизованого Android-пристрою; це не доказ виконання коду на хостовій ОС. Не переношу цей CVE-профіль на macOS без джерел. [Advisory](https://github.com/microsoft/UFO/security/advisories/GHSA-5cjx-4375-4877).
6. **Пороги «мінімум7–8B», «обов’язково RTX12GB» не є універсальними вимогами.** Вони залежать від задачі й розміщення LLM. У нашій погодженій схемі складний текст може йти хмарній моделі з лімітом, а локальне ASR уже працює на M1. Нову GPU для цього плану не обґрунтовано.
7. **Ізоляція мережею не “повністю знешкоджує” ексфільтрацію.** Дозволений endpoint сам може стати каналом витоку. Це зменшення ризику, не абсолютна гарантія.

Ці уточнення не скасовують користі дослідження: список платформ придатний як початок відбору, але оцінки «висока стабільність» і «мінімальна атака» не замінюють перевірку нашого сценарію.

## Конкретний шлях перевикористання

```text
Клавіша / текст → наш локальний клієнт + Parakeet
                 ├─ прості команди → перевірені дії Mac
                 └─ складна задача → Goose → дозволені MCP/API-інструменти
                                      ├─ чернетка / підтвердження
                                      └─ довга задача на окремому worker
```

Код, який усе ще потрібен: адаптер сесій/stream/cancel/approval між UI й Goose; невеликий набір типізованих Mac-дій; фінальна перевірка підтверджень; облік бюджету. Код, який беремо готовим: agent loop, провайдери, сесії, recipes/MCP orchestration. Для Gmail на першому етапі краще draft API, ніж браузерний агент з усім профілем користувача.

Наявність інтерфейсу MCP у двох програм не гарантує, що одна автоматично є клієнтом іншої: треба перевірити client/server ролі, транспорт і доступні endpoint-и.

## Перевірка перед переходом

Окремий невеликий compatibility spike, без видалення чинного прототипу:

1. Вибрати й зафіксувати версію Goose; перевірити CLI/runtime на Mac14.5, процес, порти та фонові ресурси. Не включати всі extensions.
2. З’єднати текстовий ввід із сесією; перевірити streaming, помилку провайдера і Cancel.
3. Підключити 3 вузькі дії: відкрити програму, відкрити URL, підготувати чернетку без send. Довести, що скасування/відмова не виконує дію.
4. Перевірити 10–20 фраз з нашим Parakeet; окремо виміряти прямий і LLM-шляхи. Виміряти $/задачу і token usage, не лише перший токен.
5. Лише після цього обирати конфігурацію/adapter як основу. До цього жоден кандидат не оголошується production-ready чи гарантовано швидшим.

У цьому дослідженні перелічені кроки не виконувалися. Результат — обґрунтований напрям наступної перевірки, не вже здійснена міграція.
